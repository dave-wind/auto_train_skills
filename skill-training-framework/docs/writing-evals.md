# 怎么写好 evals 和 expectations

`evals/evals.json` 是你的训练集。质量直接决定训练效果。

## 一个 eval 长什么样

```json
{
  "id": 1,
  "name": "descriptive-test-name",
  "prompt": "用户实际会输入的 prompt(真实、有上下文、有细节)",
  "expected_output": "人类可读的成功标准描述",
  "files": [],
  "expectations": [
    "可客观验证的断言 1",
    "可客观验证的断言 2",
    "可客观验证的断言 3"
  ]
}
```

## prompt 怎么写

**目标**:像真实用户会输入的样子。

好:
- 有具体上下文("销售额在 C 列,成本在 D 列")
- 有口语化表达("帮我搞个"、"快速搞定")
- 有不完美(typo、缩写、不规范大小写)
- 长度多样

差:
- "测试 skill 的 X 功能" ← 你在测 skill,用户不会这么说
- "Format this data" ← 抽象,无具体上下文
- 全是完美书面语 ← 不真实

## expectations 怎么写

**目标**:每条都能被一个独立读者(或 LLM grader)在没有上下文的情况下判断 通过/不通过。

### 三个原则

#### 1. 客观,不主观

好:`输出包含完整的执行命令(以 "python" 或 "bash" 开头)`
差:`输出质量很好`

#### 2. 单一断言

好:
- `提出了至少一种方案`
- `展示了分步计划`

差:
- `提出了方案、等待确认、并且选了最佳方案` ← 三件事混在一起,grader 不知道哪部分失败

#### 3. 描述"什么会出现",不是"什么不能出现"

好:`输出第一句是结论,而不是解释`
差:`输出不冗长`("冗长" 怎么定义?)

### 数量建议

- 每个 eval 4-7 条 expectations
- 太少 → 信号弱,看不出进步
- 太多 → 评分噪声大,而且写不出真正独立的 7+ 条

## 一个 evals 集合应该覆盖什么

参考:**等价类划分 + 边界用例**

对一个 skill,设计 4-6 个 eval,覆盖:

1. **典型 happy path**(最常见用法)
2. **边界:输入很短/很长**
3. **边界:用户语言/语气变化**(中/英、严肃/随意)
4. **特殊指令**(如 "just do it"、"skip"、"详细解释")
5. **可能误触发的场景**(skill 不该激活,但表面相关)
6. **复杂多步任务**

## 反模式 — 这样写会害死自己

### 反模式 1: 把 SKILL.md 的字面措辞当 expectation

差:
- `输出包含 "Step 1: xxx"`(这是 SKILL.md 的小标题)

你这是在测 "模型有没有抄 skill 里的字",不是测它有没有理解。

好:
- `输出按步骤组织,每步有明确的交付物`

### 反模式 2: 一个 eval 只有 1-2 条 expectations

信号太弱,一轮跑下来 pass_rate 不是 0% 就是 50% 或 100%,没有梯度。

### 反模式 3: 所有 eval 长得太像

5 个 eval 都是同一种任务类型。这只能证明 skill 在这一类任务上的表现,泛化性看不出来。

### 反模式 4: expectations 改成跟 SKILL.md 一一对应

你写了 6 条规则在 SKILL.md,然后写了 6 条 expectations,每条对应一条规则。
这就是过拟合的开始——你只在测 "模型听不听话",而不是 "用户感受好不好"。
应该从**用户视角**写 expectations,而不是从 skill 作者视角。

## 维护 evals 的纪律

- evals.json 跟 SKILL.md 一起进 git
- 改 expectations 的 commit 要写清楚为什么改
- 不要为了让某条总是通过就把它删掉(那是作弊)
- 失败 5 轮以上的 expectation,认真考虑:是模型做不到,还是 expectation 写得不好?

## 单轮执行环境的注意事项

框架用 `claude -p` 跑 eval,这是**单轮非交互**的——模型只有一次输出机会,不能中途等待用户回复。

写 expectation 时要注意:**不要同时要求"等待用户交互"和"输出完整结果"**。单轮里模型要么等(不给结果),要么给结果(不等),两者矛盾。

如果 skill 设计了交互式流程(如确认、选择、分步等待),expectation 应该描述单轮内可见的行为(如"呈现了选项并给出推荐"),而不是交互流程(如"询问用户并等待回复")。
